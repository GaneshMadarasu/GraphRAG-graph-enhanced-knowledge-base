🏥 Healthcare GraphRAG

An AI system that reads thousands of medical documents and answers complex research questions by connecting facts across all of them

Python 3.11 FastAPI Neo4j 5.x ChromaDB Claude all-MiniLM-L6-v2 (ONNX) Pydantic v2 Docker

What is this?

Plain English Overview

No jargon. Just plain English.

🔍

Think of it like a super-smart librarian

Imagine a librarian who has personally read every medical research paper, every internal hospital report, every news article, and every doctor's email in the building. When you ask a question, she doesn't just look up one book — she connects clues across hundreds of documents to give you the full picture.

🕸️

It builds a "mind map" of medicine

As it reads each document, it extracts facts like "Metformin treats Type 2 Diabetes" and "Metformin interacts dangerously with Furosemide" and stores them as a giant connected web — like a mind map. When you ask a question, it walks along the web to find related facts you never would have found with regular search.

⚖️

It knows who to trust more

A fact from a peer-reviewed research paper gets a higher trust score (1.0) than a fact from an informal Slack message (0.4). When it shows you an answer, it tells you exactly where each fact came from and how confident it is — and always warns you about dangerous drug interactions, no matter what.

Step by Step

What Happens When You Ask a Question?

Like a comic book — one panel at a time.

1

📝 You type a question

For example: "Which drugs interact negatively with Metformin in diabetic patients over 65?" — You send this to the API at POST /query.

2

🔎 The API spots the medical words

The Hybrid Retriever scans your question and finds known medical entities — it detects metformin (a drug) and diabetes (a disease). These become the starting points for two simultaneous searches.

3

🧮 Search #1 — Vector Search (finds similar text)

ChromaDB converts your question into a list of numbers (a "vector embedding") and finds the 10 text chunks that have the most similar meaning — like Google, but only searching your private medical documents. Each result gets a similarity score.

4

🕸️ Search #2 — Graph Search (follows connections)

Neo4j walks along the knowledge graph starting from "Metformin" and follows its edges: INTERACTS_WITH → Furosemide, CONTRAINDICATED_FOR → Heart Failure, CAUSES_SIDE_EFFECT → Lactic Acidosis. Each hop (step away) gets a graph hop score.

⚠️

⚠️ Drug interactions are always flagged — no matter what

If any drug interaction is found in the graph, it is always included in the warnings list, even if the confidence score is low. Safety comes first.

5

⚖️ Scores are fused and ranked

Every result gets a final score: 0.4 × vector score + 0.4 × graph hop score + 0.2 × source credibility. A research paper gets credibility 1.0; a Slack message gets 0.4. Results are sorted from best to worst.

6

✍️ Claude writes the answer from the evidence

The top results are sent to Claude with strict instructions: only use facts from the evidence, always cite the source document, never invent drug dosages. It writes a clear human-readable answer with inline citations like [Document: Research Paper 1].

7

✅ You receive the full response

The API returns: the answer, a confidence percentage (0–100%), the sources used, any drug interaction warnings, the list of graph entities that were queried, and a safety disclaimer.

Why Was It Built This Way?

Key Design Decisions

Every choice has a reason. Here's the thinking behind the big ones.

🕸️

Why use a graph database (Neo4j) instead of a regular database?

Drug interactions are naturally a network. Drug A interacts with Drug B, which is contraindicated for Disease C, which is comorbid with Disease D. In a regular database (like Excel or MySQL), answering "what diseases are 2 hops away from Metformin?" would require 50+ joins. Neo4j answers it in one query by following edges — like following strings on a corkboard.

✂️

Why cut documents into 800-character chunks?

AI language models (like Claude) can only read a limited amount of text at one time — like reading one page at a time. If you give them an entire research paper, the important sentence about drug interactions might get buried. By cutting into 800-character pieces, you make sure each piece is small enough to be meaningfully searched and fed to the AI.

🔤

Why normalize drug names before storing them?

Medical documents are messy. One paper says "Metformin," another says "Glucophage," another says "dimethylbiguanide." Without normalization, you'd have 3 separate nodes for the same drug, and a query for "Metformin interactions" would miss the other two. The normalizer maps all 3 → "metformin" before storing, so the graph stays clean.

⚖️

Why combine vector search AND graph search?

Each method has a blind spot. Vector search is great at finding text that sounds similar but misses logical connections (it doesn't know Drug A and Drug B are related just because they share a node). Graph search finds connections but can miss relevant text that doesn't use exact entity names. Combining both gives answers that are both semantically relevant and logically connected.

🛡️

Why always show drug interaction warnings even at low confidence?

In medicine, a missed drug interaction can kill someone. So drug interaction warnings are surfaced unconditionally — even if the overall confidence score is low. The system is designed so that safety information is never filtered out by an algorithm, even if the evidence is weak. The user can decide how to act on it.

Words You Might Not Know

Glossary

Every technical term used in this project — in plain English.

Vector Embedding
A list of ~1536 numbers that captures the "meaning" of a sentence. Two sentences with similar meaning will have similar number-lists, so a computer can find them by comparing numbers.
Graph Database
A database that stores things as nodes (dots) and relationships (lines between dots). Perfect for medical data where everything is connected — drugs connect to diseases connect to genes.
RAG (Retrieval-Augmented Generation)
A technique where an AI first searches a database for relevant facts, then uses those facts to write an answer — instead of relying on what it memorized during training. This prevents made-up answers.
GraphRAG
RAG + a knowledge graph. Instead of only searching for similar text, it also walks connections in a graph — finding facts that are related by logic, not just by wording.
Cypher
The query language used to ask questions to Neo4j. Like SQL is for regular databases, Cypher is for graph databases. Example: MATCH (d:Drug)-[:INTERACTS_WITH]->(d2:Drug) means "find all drug-drug interactions."
MERGE (Neo4j)
A Neo4j command that means "create this node/relationship if it doesn't exist yet; update it if it does." Prevents duplicates when ingesting the same drug from 10 different documents.
Chunk
A small piece of a document (800 characters in this project). Documents are split into chunks so the AI can search and process them piece by piece.
Fuzzy Matching
Finding a match even when the spelling isn't exact. Used in the Entity Normalizer to match "Tylenol" to "acetaminophen" even with slight typos or variations.
Score Fusion
Combining multiple scores into one final score. Here: 40% from semantic similarity + 40% from graph connection strength + 20% from how trustworthy the source document is.
Entity Extraction
Reading a text and pulling out specific types of "things" — like drug names, disease names, and gene names. In this project, Claude does the extraction.
FastAPI
A Python framework for building web APIs quickly. It automatically generates interactive documentation at /docs so you can test every endpoint in your browser.
Credibility Score
A number (0.4 to 1.0) assigned to each document type based on how trustworthy it is. Research papers score 1.0 (peer-reviewed). Slack messages score 0.4 (informal).
