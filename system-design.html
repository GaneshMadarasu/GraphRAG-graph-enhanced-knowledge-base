GraphRAG

A smart knowledge base that reads your documents, maps how facts connect, and answers questions with cited evidence.

Python 3.11 FastAPI Neo4j ChromaDB Claude Haiku Claude Sonnet MCP Docker spaCy sentence-transformers
What is this?

Plain English Overview

The librarian analogy: Imagine a librarian who has read every document in a library and drawn a giant mind-map showing how facts connect — "Bell Labs invented the transistor", "the transistor led to the microprocessor", "Intel mass-produced the microprocessor". When you ask a question, they search the mind-map and do a quick keyword scan at the same time, then hand your answer to a writing assistant who turns those raw facts into a clear, cited response.

Two phases: teach, then ask. First you feed it documents (.txt, .pdf, .md). It reads each one, cuts it into manageable pieces, asks Claude to identify the important things (people, places, technologies) and how they connect, then stores everything in two databases — one shaped like a web of connections, one shaped for fast meaning-based search.

When you ask a question, both databases are searched at the same time. The results are blended, scored, and handed to Claude Sonnet, which writes a grounded answer using only what it found — no guessing.

Why two databases? Each one is good at a different kind of question. The graph database (Neo4j) is great at "how are these two things connected?" — it follows relationship chains like a detective. The vector database (ChromaDB) is great at "what text is closest in meaning to my question?" — it finds relevant paragraphs even when the words don't match exactly.

MCP layer. A new Model Context Protocol server lets Claude Desktop and Claude Code call the knowledge base directly mid-conversation — no terminal, no curl commands needed.

Step by step

What Happens When You Ask a Question?

Here's the exact journey from your question to the final answer.

1
📝 You type a question e.g. "What did Alan Turing contribute to Bletchley Park?" — sent via Claude Desktop (MCP) or directly to the FastAPI endpoint POST /query.
2
🔤 Named entities are extracted from your question spaCy's NLP model reads the question and pulls out proper nouns — "Alan Turing", "Bletchley Park". These become the seeds for graph search.
3
⚡ Two searches fire in parallel (at the same time) The Graph Retriever walks Neo4j looking for "Alan Turing" and "Bletchley Park" — finding 1-hop neighbors and the shortest path between them. The Vector Retriever converts your question into a list of numbers and finds the top-5 most similar document chunks in ChromaDB.
4
⚖️ Results are merged and scored Vector results × 0.6 + Graph results × 0.4. Duplicates are removed (same chunk from both sources keeps the higher score). Top 5 items move forward.
5
🤖 Claude Sonnet writes the answer The merged context (graph facts + text chunks) is formatted and sent to Claude Sonnet with a strict prompt: "Answer using ONLY this context. Cite your sources." Claude cannot hallucinate beyond the retrieved evidence.
6
✅ You receive a grounded answer The response includes the answer text, the chunk IDs used as sources, and the entity names from the knowledge graph. Claude Desktop shows this inline in the conversation.

Graph Builder
Writes extracted entities as nodes and relationships as edges into Neo4j. Also links each entity back to the source chunk so you can trace where every fact came from.
"Like pinning sticky notes to a corkboard and connecting them with labeled strings."
Neo4j · Cypher
IN: entities + relationships OUT: graph nodes + edges
📐
Vector Store
Converts each text chunk into a list of ~384 numbers (an "embedding") that captures its meaning, then stores them in ChromaDB for fast similarity lookup. Runs entirely on your machine — no API call needed.
"Like giving every chunk a GPS coordinate based on its meaning — nearby coordinates = similar meaning."
ChromaDB · all-MiniLM-L6-v2
IN: text chunk OUT: stored embedding
🔍
Graph Retriever
At query time, extracts named entities from the question using spaCy, then runs Cypher queries against Neo4j: 1-hop neighbors for each entity, plus shortest path between multiple entities (up to 4 hops).
"Like a detective following leads — start with a name, see who they connected with, find the path between two suspects."
spaCy · Neo4j Cypher
IN: question OUT: graph triples + paths
🎯
Vector Retriever
Converts the question into an embedding, then asks ChromaDB for the top-K chunks whose embeddings are closest in meaning. Works even when the question uses different words than the document.
"Like searching for songs by humming the tune — it finds matches by feel, not by exact words."
ChromaDB ANN · cosine similarity
IN: question OUT: top-K chunks + scores
⚖️
Hybrid Retriever
Runs graph and vector retrieval in parallel using asyncio, then fuses their scores (vector × 0.6 + graph × 0.4), deduplicates by chunk ID, and returns the top-K unified results.
"Like two expert witnesses giving testimony simultaneously — a judge then weighs both opinions into one verdict."
asyncio · score fusion
IN: question + top_k OUT: ranked context items
💬
Answer Generator
Formats the retrieved context items (graph facts + text chunks) into a structured prompt and sends it to Claude Sonnet, which writes a grounded, cited answer using only the provided evidence.
"Like a barrister who can only argue using evidence already admitted — no improvising."
Claude Sonnet · Anthropic SDK
IN: question + context OUT: answer + sources
🔌
MCP Server
Wraps the five core operations as MCP tools exposed over stdio. Claude Desktop and Claude Code can call query_knowledge_base, get_entity, ingest_documents, get_stats, and health_check directly mid-conversation.
"Like a universal adapter plug — Claude plugs in and the knowledge base becomes one of its hands."
mcp · FastMCP · stdio

The HTTP interface — exposes POST /ingest, POST /query, GET /health, GET /stats, GET /graph/entity/{name}. Also serves the GraphRAG Explorer web UI. Runs on port 8000 via Uvicorn.
"The front desk — it routes every incoming request to the right back-office team."
FastAPI · Uvicorn · Pydantic

Data

What Gets Saved Where?

Neo4j is like a web of sticky notes — each note is an entity (a person, place, or concept) and colored strings connect notes that are related, with a label on each string saying how they're related. ChromaDB is like a filing cabinet where each drawer is labeled with a meaning-fingerprint, so you can pull out the most relevant folder just by describing what you're looking for.

What Where Why that store?
Entity nodes (people, orgs, concepts, technologies…) Neo4j Graph databases are built for "who connects to whom" — fast traversal, no joins needed
Typed relationship edges (CREATED, WORKED_AT, INFLUENCED…) Neo4j Relationships are first-class citizens in Neo4j — you can query the connection itself, not just the nodes
Chunk → Entity links (MENTIONED_IN) Neo4j Lets you trace every entity back to the exact source text that mentioned it
Text chunk embeddings (vectors of ~384 numbers) ChromaDB ChromaDB's HNSW index finds nearest neighbors in milliseconds — exact cosine search at scale
Chunk text + metadata (filename, chunk index) ChromaDB Stored alongside the embedding so retrieval returns the actual text, not just an ID
ChromaDB data files Local disk (./chroma_db/) Persists across restarts — no re-ingestion needed after a reboot
Architecture

Key Design Decisions — Why This Way?

Why two databases instead of one?

Vector search finds semantically similar text but misses factual connections ("Bell Labs invented the transistor — which led to Intel — which created Moore's Law"). A graph database follows those chains in one query. Neither alone would answer both types of questions well — together they cover each other's blind spots.

Why 60% vector / 40% graph weighting?

Empirically, semantic search catches more relevant chunks on open-ended questions. Graph results are more precise but narrower (they require exact entity matches). The 60/40 split rewards breadth while still giving factual relationship chains a meaningful boost.

Why Claude Haiku for extraction and Claude Sonnet for generation?

Extraction runs on every chunk during ingestion — potentially thousands of API calls. Haiku is fast and cheap enough for this volume. Generation happens once per query and needs more reasoning capability to synthesize evidence into a coherent answer — that's where Sonnet's quality earns its cost.

Why local embeddings (all-MiniLM-L6-v2) instead of an API?

Embeddings are computed for every chunk at ingest time and every query at search time. Using a cloud API would add latency, cost, and a network dependency. The local model runs entirely on your machine — faster, cheaper, and works offline.

Why add an MCP server on top of the existing FastAPI?

FastAPI is for programmatic access (scripts, pipelines, the web UI). MCP is for conversational access — Claude can call the knowledge base mid-sentence without you copy-pasting results. Both interfaces coexist: the same Python functions underpin both, with no duplication.

Reference

Words You Might Not Know

Vector embedding
A list of numbers (e.g. 384 of them) that represents the meaning of a sentence. Similar sentences produce similar number lists — so you can search by meaning, not just keywords.
Graph database
A database that stores connections between things (nodes and edges), not just rows and columns. Neo4j is the most popular one — great for "how are A and B related?" questions.
RAG (Retrieval-Augmented Generation)
A technique where you fetch relevant facts first, then give those facts to an AI to write the answer — so the AI can't make things up, it can only use what you gave it.
Cosine similarity
A maths trick for measuring how similar two vectors are. If two vectors point in nearly the same direction, they're similar (score close to 1.0). Opposite directions = score near -1.0. Used to rank search results.
HNSW index
Hierarchical Navigable Small World — a clever data structure inside ChromaDB that makes nearest-neighbor search extremely fast, even with millions of vectors.
Cypher
Neo4j's query language — like SQL but for graphs. Instead of SELECT rows, you MATCH patterns like (Alan Turing)-[:WORKED_AT]->(Bletchley Park).
NER (Named Entity Recognition)
The job of finding proper nouns in text — "Alan Turing" (person), "Bell Labs" (organisation), "New Jersey" (location). spaCy does this here to identify what to look up in the graph.
MCP (Model Context Protocol)
A standard that lets Claude call external tools during a conversation. The tool returns data, Claude reads it and continues — like giving Claude hands to reach out and fetch information.
Chunking
Cutting a long document into smaller pieces (chunks) so an AI model — which can only read a limited amount at once — can process each piece. Overlapping chunks prevent facts from being cut in half.
Score fusion
Combining scores from two different search systems (graph + vector) into one unified ranking. Here: final score = vector score × 0.6 + graph score × 0.4.
